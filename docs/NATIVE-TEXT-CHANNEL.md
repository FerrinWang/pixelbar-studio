# 原生文字通道调查

2026-10-13：只读检查本机安装的 TempoHub 对 PixelBar 的调用逻辑，未注入驱动、未抓取账号认证、未改动驱动文件、未向设备发送探测指令。以下是静态协议线索，不等同于实屏验证。

## 已核对的发送路径

- QQ音乐歌词行 → UTF-8 编码 → 文字设置指令 `E8`，来源 `0x0E`。短行请求体为 `[sourceId,totalUTF8Bytes,...textBytes]`；原厂歌词代码以55字节切长行，各包重复来源与总长度，没有图片上传的起始/结束握手。
- 新闻类别来源：热点 `0x09`、娱乐 `0x0A`、生活 `0x0B`、社会 `0x0C`。经共用文字发送模块进入 `E8`。
- 天气来源 `0x0D`，也经共用文字发送模块进入 `E8`。
- 共用模块先通过 `E7` 查询来源的文本容量和每包容量，而非盲目假设所有来源均55字节。响应解析字段为 `[sourceId,textMaxLength,packageMaxLength,textLength,...UTF8Bytes]`。发送总UTF-8长度最多255；清除换行和制表符后按原厂像素文本宽度与字节长度裁切。
- 本机驱动中 E7/E8 枚举未带高字节，报文封装映射到 EC 类型；它们与现有适配器中的图片 `17` 上传流程是不同命令。需要实机确认，不据此修改既有查询/上传路径。

## 能与不能据此判断的事情

可以确认原厂不是将每句歌词、新闻和天气统一转换为上传图片。这是可尝试实时文字更新的独立入口，中文由固件渲染的可能性很高。

尚未确认：自定义文字是否被固件接受；是否完全不显示上传提示；来源能否脱离原厂登录/模式设置独立工作；换字速度、滚动行为和恢复行为。未发现这些文本请求体包含任意像素、坐标、字体选择或进度条，因此不能把它等同于自由画布通道。

## 首轮上传期间覆盖实验

2026-10-13 用户明确要求测试上传图片时插入文字。设备可连接、伴侣自动推送关闭。E7/EC 来源14返回文本容量80、分包容量50；实验短文字「屏幕更新中」为15字节UTF-8。

采用独立开发探测程序，不修改正式引擎：从用户已保存场景生成两帧、500ms冒号动画（raw 2048字节、传输2128字节），保留屏幕色调。上传ready之后发送一次E8/EC文本；约一半数据块确认后再发送一次，块间临时留80ms便于观察。完整上传及逐块确认通过，最终读回原7/15模式和#71FF56。这仅证明混发未使本次上传失败，不证明文字曾可见、成功遮挡或普遍兼容；视觉结果等待用户观察反馈。未改本地保存场景、灯光或固件。

## 后续实屏验证与正式静默更新

用户观察：上传期间插入歌词文字无法遮挡提示；新闻单独推送可见。先发送新闻、约3秒后上传明显不同的 NEW IMAGE 画面，新闻保持显示，退出后新画面生效。

提示音使用 EC `86 []` 查询：本机返回 `[14,1,1]`。在原版 sound_box 映射中，配置14第1项为蓝牙，第2项为消息（原厂界面隐藏此项）；EC `87 [14,2,0]` 关闭消息提示音。读回 `[14,1,0]` 后推送新闻，用户确认无提示音。恢复 `87 [14,2,1]`，读回原数组通过。仅此型号/配置验证，不适用 AI/hz 型号的同编号映射。

正式引擎 push/animation 默认统一采用：查询原设置和文字容量 → 临时关闭并读回确认 → 来源9新闻更新提示文字 → 等待1.5秒 → 原画布上传 → 恢复原消息开关并读回确认。额外等待曾从3秒改成0.5秒，用户反馈太短后改为1.5秒；当前视觉效果待实屏验证。新闻本身驻留时间没有已验证的调节参数，不承诺总显示时间精确为1–2秒。普通失败路径也执行恢复；原设置或容量未知时停止，不盲写、不偷偷回退有声上传。蓝牙提示音、播放音量、灯光不改。自动推送仍保持相同画面的去重逻辑。

网页可编辑更新前文本。按用户要求，不设置人为字符数上限，允许方块/空格自行测试，未改成默认居中。协议255字节上限、E7实际容量及控制字符检查仍保留；本机最大为 `min(80*3,255)=240` UTF-8字节，超过时报错，不截断、也不修改提示音。网页默认文字仍为短文本「屏幕更新中」。
