# 实验性多帧上传

> 当前设备 / 7-15 槽位实测可用边界：60 帧。恰好 60 帧的 63840 字节完整传输，设备模式读回成功，用户确认循环到 060 / 60。64 与 128 帧均在第 1276 个传输包返回提前结束（已发送约 63850 字节）；128 帧实屏只播放到 060 / 128 后循环。不能把开始播放等同于全部帧已接收。网页、API、正常命令均限制为 60 帧；探测命令另行限制 256 帧，不面向常规上传。

## 本机证据

TempoHub 的非时钟场景选择代码会在需要加载素材时调用图片传输；文件名是场景与模板编号。时钟分支被显式排除，不能据此认为时钟同样可替换。

本机赛博缓存 7_1 的文件大小为 2128 字节，7_15 为 8512 字节，分别对应 2 与 8 个 1064 字节帧。每个 133 字节记录包含 5 字节头和 128 字节像素；记录头为 `[7, segmentHigh, segmentLow, delayHigh, delayLow]`。段索引连续递增，8 段构成 256×32 的一帧。观察到的 delay 字段为 100；实际时间单位、最大容量、循环行为尚需实机验证。

原厂缓存不随项目分发；仅使用自行生成或用户拥有的图片。

## 当前入口

画面质量尚未完全验收：用户在 60 帧中发现撕裂，34 帧、delay=1000 慢速对照仍确认固定发生在第 32 帧。照片显示异常位于左上角，底部进度条完整；因此撤回“最后一个像素块的段编号 255 / 0xFF 导致右下角损坏”的定位假设。自行生成的第 32 帧首个 128 字节像素块已核对，原始数据无照片中的条纹；其记录起点为文件偏移 32984，接近 32 KiB 边界，但尚不能证明是存储边界问题。正在用交换第 1 / 32 帧内容的对照区分内容与位置相关异常，目前没有修复证据。网页 32 帧及以上需勾选实验确认，普通使用建议暂控制在 31 帧以内；60 帧是接收 / 循环容量验证，不是无撕裂保证。

交换第 1 / 32 帧后，用户确认异常出现在第 32 个播放位置（此时画面编号为 001），而不是被移到开头的编号 032。此结果排除了仅由编号 032 的图像内容引起的解释。后续每次传输 ACK 后增加 50 ms 缓冲、使用原始 34 帧和 delay=1000，用户确认仍然撕裂，因此该缓冲试验无效；不修改正式上传路径。下一项对照改用已观察到的赛博模板 7/1，其余帧数据、记录编码、播放间隔及正常传输节奏不变。注意模板选择发生在传输完成后，不能假定模板具有独立存储槽位；此试验只检查模板相关行为。

7/1 模板对照：36176 字节完整发送且模式读回为 7/1，但用户报告仍停在“图片上传中…”，没有正常起播。因此此组合不能作为可用动画路径，也不能据此比较第 32 帧撕裂；已尝试恢复用户保存的普通画布。此结果进一步表明完整传输 ACK / 模式读回不等于播放成功。正式版本继续使用已验证可以起播的 7/15，不合入模板切换试验。

用户确认普通画布恢复后，下一项对照截取原始 34 帧文件的前 32 帧，保留每一像素与 delay=1000，仅去掉第 33 / 34 帧，使用正常 7/15 模板与传输节奏。画面标签仍为 `001 / 34` 至 `032 / 34`，不能误读为上传了 34 帧；文件像素 32768 字节、设备记录 34048 字节。第 32 帧记录起点 32984、段编号 248–255；文件 32768 边界实际落在第 31 帧段编号 246 的记录内（记录内偏移 50），所以不能仅凭接近 32 KiB 将故障断言为该文件边界。此对照等待实屏确认，不视为修复。

恰好 32 帧对照完整传输并读回 7/15，用户确认第 32 帧仍撕裂，因此异常不依赖第 33 / 34 帧存在。下一项定位对照将这 32 帧的首个 128 字节像素块全部清零（x=0..127、y=0..7），其余像素、帧头与 delay 不变；等待用户确认是否仍在全黑区域出现条纹。不合入正式编码，也不视为修复。

网页的「动画上传」面板支持：

- 收集当前画布，修改布局后再收集下一帧；最多 60 帧，可选择预览帧或删除选中帧。
- 导入 2–60 张 PNG / JPEG / WebP，按文件名排序，缩放到 256×32 并以固定阈值 128 转换。尚未支持直接解码 GIF；不要把 GIF 第一帧当作已支持动图。
- 本页动画预览；预览暂按毫秒解释间隔，仅供设计，不是硬件计时验证。
- 导出 / 导入 `pixelbar-animation-v1` JSON。动画帧不会自动存进普通场景；关闭页面前请导出。
- 一次上传，多帧打包。上传成功关闭自动图片推送，防止后台覆盖；上传失败恢复上传前的自动设置。

上传使用已观察到的赛博槽位 7 / 15，会替换该槽位设备上的素材，不修改电脑中的原厂缓存。可从原厂驱动重新加载原素材。恢复自由画布可手动推送或重新开启自动推送。

首次上传仍会出现固件提示。成功 ACK 和模式读回只说明传输与模式设置成功，不能证明播放、间隔、循环或无二次提示。

## API

`POST /api/animation`，本机会话鉴权、同源限制与现有接口一致：

```json
{"frames":["<1024-byte frame in base64>","<another frame>"],"delay":1000}
```

2–60 帧，delay 整数字段 100–60000，默认 100（已用于实机播放验证）。每帧 1024 字节，设备文件每帧 1064 字节，USB 报文开销另计。60 帧像素为 61440 字节、传输文件为 63840 字节、133 字节记录共 480 个。JSON 中 base64 像素字段总计 82080 个字符，另有 JSON 键名 / 标点开销。其他 delay 值与实际时间单位尚未验证。

上传超时上限为 120 秒，网页等待 135 秒；Engine 通过 stderr JSON Lines 提供已确认字节进度，不混入 stdout 的最终 JSON。设备提前返回结束时报告 `upload_truncated`，不得报完整上传成功。首次提示持续数十秒并不等于卡死；以 ACK 进度和最终状态判断。

16 帧首次测试的异常未定位，后续 17、32、60 帧均成功，原先 16 KiB 容量猜测已被证伪。60 帧边界仅适用于当前设备、固件与编码 / 槽位，不推断其他型号或固件版本。

## 不能替代的功能

动画是预先计算的内容，不是设备脚本。实时 Codex 用量变化仍需重新上传。预先制作多分钟时钟也需要验证长帧间隔、起播同步和循环，当前版本不承诺长期准确走时。下一步可验证长间隔与同步，再考虑 GIF 解码和定时生成。
